## [Unreleased]
### Added
- `install.sh --update` refuses to downgrade. A release or tag older than the installed version is refused (a pre-release counts as older than its release). A source build records the commit it was built from in `/etc/mirymesh/installed_commit`; a later update is refused when that commit is not part of the history of the commit it would install. This catches what the version number cannot, because source builds report `dev`: for example moving a host built from `master` to the `release` branch before the change has been merged there. The check runs before anything is installed or changed. `--allow-downgrade` skips it. Hosts built before this change have no record yet, so only the version check applies to their first update. Source builds now clone the full history instead of `--depth 1`. The Nodes page "更新" button is not covered.
- Source builds made by `install.sh` (Master and DataNode) now report the version `<7-char commit>-dev`, for example `1f7b438-dev`, instead of `dev`. `--version TAG` still stamps the tag. The value is not a semantic version, so the update notice, the DataNode update target and the downgrade check treat it the same as `dev` before. `mirymesh-controller --version`, the DataNode registration and the Nodes page now show which commit a host runs. A plain `go build` still reports `dev`.
- Add a disk to a DataNode from the Master. The Nodes page has a "ディスク追加" button for online nodes, and `POST /api/admin/nodes/disks` with `{"node_id": "...", "path": "/mnt/disk2"}` does the same. The Master forwards the path to the new `POST /internal/paths` on the DataNode with that node's own token. The DataNode checks that the path is absolute, writable and does not overlap an existing disk, opens a store for it, starts reporting it to the Master and keeps it in `<data dir>/datanode.paths.json`, which is merged with `config.yaml` at startup (so `install.sh --path` rewriting `config.yaml` does not lose it). Disks can only be added, never removed or reduced. The systemd unit uses `ProtectSystem=strict`, so a path outside `ReadWritePaths` (for example a new mount point) is refused with the reason; use `install.sh --path` on that node first. A node running an older version answers `409` until `install.sh --update` is run on it.
- Admin Token can be reissued from the console. The Settings page has an "Admin Token" card with a "Rotate Admin Token" button, and `POST /api/admin/rotate-token` (authenticated with the current token) does the same and returns `{"admin_token": "..."}` with `Cache-Control: no-store`. The new token is saved in `setup.admin_token`, every existing session is revoked and a new 24h session is opened for the new token, all in one transaction. The old token stops working at once. The browser that rotated the token switches to the new one and stays signed in. The new token is shown once; replace it in any CLI or script that uses it. DataNode credentials do not change: the secret they are derived from is fixed when the Master starts, so paired nodes keep working. As noted below, restart every node once before rotating if the node was paired by an older Master.
- Each DataNode now gets its own random node token. The Master creates it when the node registers (pair token, or an existing node that re-registers), stores it encrypted with `MIRYMESH_MASTER_KEY` in the new `node_tokens` table (migration `0006`, MySQL version included), and uses it for every call to that node (objects, update). The token no longer depends on the Admin / internal token, so changing that token does not cut paired nodes off. DataNodes need no database; they keep the token in `datanode.token` as before. Nodes paired by an older Master migrate when the DataNode next registers, which happens on restart; updating the Master alone does not migrate them, and they keep working with the old token until then. The old derived token is accepted at `/internal/register` (so a node whose response was lost can retry) and, for every other call, only until the node has a stored token. Restart every node once before changing the Admin token. `RotateMasterKey` re-seals `node_tokens` together with the other secrets. If the database loses a node's token, pair that node again with a new pair token.
- `install.sh` always verifies the role before it changes anything and prints the facts it used: the recorded role, the enabled/active state of `mirymesh-controller` and `mirymesh-datanode`, `controller.env` and `datanode.token`. A contradiction (for example Master on a host with a DataNode token or service) stops the run; `--force-role` overrides. After the run it checks that `/etc/mirymesh/role` was written and that a paired DataNode still has its `datanode.token`, and warns when a controller is running on a DataNode host. New `--check-role` prints these facts and the detected role and exits without changing anything (add `--master` / `--client` to test a role).
- `install.sh` records the host role in `/etc/mirymesh/role` (`master` or `client`) after every install or update, and role detection trusts that file first. A run whose role differs from the record (for example `--master` on a DataNode host, or an auto-detected role) stops with an error before any database, `controller.env` or service change. Hosts installed before the record existed are checked for `/var/lib/mirymesh/datanode.token` and refused as Master if it exists. `--force-role` overrides the guard.
- `install.sh` (Master) can choose between PostgreSQL and MySQL/MariaDB when both are installed: an interactive prompt, `--db-driver postgres|mysql`, or PostgreSQL with `--yes`. New `--db-user`, `--db-name` and `--db-password` options.
- `install.sh` creates the MySQL/MariaDB user and database (root socket login) and hands the DSN to the controller, the same as it does for PostgreSQL.
- Update notice channel: the Settings page has an "更新のお知らせ" card to choose stable releases only, pre-releases too, or "follow the install" (the previous behavior, still the default). The choice is stored in the database (`app_settings`, migration `0005`), applies at once, and survives restarts. API: `PUT /api/admin/update/settings` with `{"notify_channel": "auto|release|prerelease"}`. `GET /api/admin/update` now also returns `notify_channel` and `include_prerelease`.
- `install.sh`: an interactive run on a host that already has MiryMesh asks where to update to: Release, Prerelease or Dev (branch). This is how a Dev source build moves to Prerelease or Release. `--update --channel release|prerelease` does the same without prompts.
- Console: the Placement tab of a bucket (`BucketDetail.vue`) now sets the placement mode (spread / same_node / any), the allow-list of disks the bucket may write to, and the disks reserved for that bucket only. Before, only the single/dual/triple/ALL policy could be chosen and the rest needed direct API calls.
- Integration tests for `RemoteStore` across several real DataNode HTTP servers (`internal/s3api/remote_store_multinode_test.go`): spreading over nodes, GET failover, merged and paged listing, delete, a node that is down, `same_node` with an allow-list, reserved disks, and per-node token rejection.
- S3 region can be changed from the console: the Settings page has an "S3 リージョン" card (presets plus free input, "既定に戻す" for `us-east-1`). The value is stored in the database (`app_settings`, key `s3.region`), applies at once without a restart, survives restarts, and overrides `server.region`. It is what `X-Amz-Bucket-Region` and GetBucketLocation report; SigV4 still accepts the region the client signed with. API: `GET/PUT /api/admin/region` with `{"region": "ap-northeast-1"}`.
- README: new "ソースビルド（Dev）のノードを更新する" section. It explains how to update a Master or DataNode that was built from a branch with `install.sh --update --dev --branch NAME`, why the Nodes page "更新" button must not be used on those hosts (it swaps in the release binary), the update order (Master first, then one DataNode at a time), and how to go back to Release or Prerelease.

### Changed
- The Master no longer writes files in gateway mode. A request body of unknown size used to be spooled to `<data_dir>/tmp`. `RemoteStore.PutObject` now streams a body whose size is known (the size passed by the S3 handler, CopyObject and the console upload) and answers `411 MissingContentLength` otherwise. `SetSpoolDir` and the spool code are removed. In gateway mode the `.evac` snapshot is not read at startup. `/internal/evacuate` and `/internal/restore` answer `503` on a process that has no snapshot directory, instead of writing to `/tmp`. Buckets, nodes, keys, settings and sub-resource documents are in the database. The only file access left is a one-time migration of a legacy `setup.json`: it is read into the database and then renamed to `setup.json.migrated-<timestamp>` in `<data_dir>`. This rename is the only file write left on the Master. If `<data_dir>` is not writable, the rename fails without an error and `setup.json` stays where it is. Tests: `internal/s3api/remote_store_spool_test.go`.

### Fixed
- A DataNode lost its identity when it was updated or its container was recreated. The node ID defaulted to the host name and was not stored, so a new container came back as an unknown node. The ID is now saved in `<data dir>/datanode.id`, next to `datanode.token`, and loaded at startup, so the node keeps its ID, token and disks across `install.sh --update`, self-update and rebuilds. The address the Master dials stays the host name the process started with. Snapshots pushed by the Master are stored in `<data dir>/.evac` on the DataNode, which is inside `ReadWritePaths`. In Docker, keep `/var/lib/mirymesh` on a volume (the dev compose file already does). Tests: `internal/datanode/node_id_test.go`.
- Updating or restarting the Master emptied the node list (the Nodes page went from `0 / 1` to `0 / 0`) and cut every DataNode off. The Master kept the node and disk list only in memory, and a DataNode that did not register again after the restart was answered with `404` on every heartbeat. The Master now stores nodes and their last reported disks in the new `datanodes` and `datanode_disks` tables (migrations `0007` and `0008`, MySQL versions included) and loads them at startup (`Registry.SetStore`, `internal/admin/node_registry_store.go`). Restored nodes start as offline and turn online on their next heartbeat, so DataNodes of an older version work without registering again. A node that is removed from the console is removed from the tables too. Tests: `internal/datanode/registry_store_test.go`.
- Buckets disappeared when the Master restarted. `RemoteStore` (gateway mode) held the bucket list and bucket policies only in memory, so a restart emptied the list even though the buckets had been created and their objects still sat on the DataNodes. `RemoteStore` now writes to the `buckets` table, the same table `Storage` uses, on create, delete and policy changes, and `LoadBuckets` reads it back at startup. An existing row is never replaced, because `placement` cascades from `buckets`. Buckets created before this change were never stored; create them again with the same name, and the objects already on the DataNodes become visible again. Tests: `internal/s3api/remote_store_buckets_db_test.go`.
- In `docker-compose.dev.yml`, recreating or rebuilding the DataNode container ended in `403`. The node ID is the container host name and changed with every new container, and `/var/lib/mirymesh` (where `datanode.token` is kept) was not a volume, so the node came back with a new ID and no token, and the one-time pair token was already used. The service now has a fixed `hostname: datanode` and a `dn-state` volume on `/var/lib/mirymesh`. Existing dev setups pair the DataNode once more after this change.
- Uploads from the console failed with `read-only file system` on the Master. `RemoteStore.PutObject` spools a body of unknown size to a temporary file, and `spoolBody` created it in `/tmp` with `os.CreateTemp("", ...)`. The systemd unit runs with `ProtectSystem=strict`, which makes `/tmp` read-only, so every console upload ended in a `500`. The Master now spools below `<data_dir>/tmp` (`s3api.SetSpoolDir`, created with mode 0700 at startup; leftover `mirymesh-put-*` files from a crashed run are removed). The console upload passes the request `Content-Length` to the store (`s3api.WithSizeHint`), so a normal upload is streamed and does not touch the disk at all. `/internal/evacuate` and `/internal/restore` on the Master wrote to `os.TempDir()` as well; they now use `MIRYMESH_EVAC_DIR` or `<data_dir>/.evac`, the same directory the Master reads at startup (`Handler.SetEvacDir`). `<data_dir>` (default `/var/lib/mirymesh`) is inside the unit's `ReadWritePaths`. If `data_dir` points elsewhere, add it to `ReadWritePaths`. Tests: `internal/s3api/remote_store_spool_test.go`, `internal/datanode/evacdir_test.go`.
- Multipart uploads through the Master did not work. `RemoteStore.CreateMultipartUpload` called `/internal/multipart/*` on the DataNode, which had no such route, so every multipart upload failed with a `404` at the first call; `RemoteStore.GetUpload` always returned nil, so parts were rejected with `NoSuchUpload` before their body was read. The DataNode now serves `/internal/multipart/uploads` (create, list, get, abort, `parts/{n}`, `complete`) with its node token (`internal/datanode/multipart.go`, `internal/s3api/datanode_multipart.go`). An upload is created on the node and disk the placement engine picks, and its parts and final object stay on that disk. `RemoteStore` sends each later call to that node (`internal/s3api/remote_store_multipart.go`); it remembers the node per upload ID in memory and asks the online nodes when it does not know the upload (for example after a Master restart). Part bodies are streamed to the node and written to a file there, never held in Master memory. If the source fails mid-part (for example a checksum mismatch), the part is not stored and the original error is returned. `CompleteMultipartUpload` uses a client with a 30 minute timeout instead of 30 seconds. S3 error codes (`NoSuchUpload`, `InvalidPart`, ...) from the node reach the client unchanged. Tests: `internal/s3api/remote_store_multipart_test.go`. Update every DataNode (`install.sh --update`) before using multipart uploads; an older node answers `404`. In gateway mode, SSE-C and checksum multipart uploads also need stored documents (the multipart config and one record per part). `RemoteStore` did not implement `SubresourceStore`, so the Router fell back to `noSubresources`, whose `PutSubresource` returns `errSubresourceUnsupported`. `RemoteStore` now keeps these documents, and ACL, tagging, CORS, lifecycle and quota documents, in the `s3_subresources` table of the Master database, or in memory when no database is attached (`internal/s3api/remote_store_subresources.go`). `cmd/controller` attaches the database at startup, so the documents survive a Master restart. Tests: `internal/s3api/remote_store_subresources_test.go` (SSE-C with a FULL_OBJECT CRC32, a COMPOSITE SHA256, persistence in SQLite across two stores, in-memory mode).
- Large objects no longer pass through Master memory. `RemoteStore.PutObject` read the whole body with `io.ReadAll` before sending it to the DataNode. It now streams the body with a `Content-Length`. `handlePutObject` passes the request size (`withSizeHint`); when the size is unknown the body is spooled to a temporary file instead of memory. A read error from the source (for example a failed checksum) is returned to the caller unchanged, and `lastByteHold` keeps the last byte back so the DataNode never stores an object the verifier rejected. Object bodies use a client without the 30s total timeout (only a 2 minute response-header timeout), so long transfers are not cut off. A `Range` GET on a non-seekable body (the DataNode response) skips the leading bytes instead of reading the whole object, and `UploadPartCopy` streams its source and range the same way. Tests: `internal/s3api/remote_store_stream_test.go`. Other `io.ReadAll` calls on request bodies (multipart completion XML, policies) are small, size-limited documents and were left alone.
- Objects read through the Master (download, direct link, `GetObject` / `HeadObject`) were answered with `Content-Length: 0`, so clients reported the file as broken even though it was stored intact. The DataNode `GET` / `HEAD` on `/internal/objects/` sent neither `Content-Length` nor `Last-Modified`, and `RemoteStore` returned an `ObjectMeta` with only `Key` and `ContentType`; `handleGetObject` takes the length from `ObjectMeta.Size`. The DataNode now sends both headers, and `RemoteStore` fills `Size`, `ETag`, `LastMod` and `x-amz-meta-*` from the response (`internal/s3api/remote_store_meta.go`). A test in `internal/s3api/remote_store_meta_test.go` checks them for GET and HEAD.
- `RemoteStore` changed its bucket map without a lock. `CreateBucket` and `DeleteBucket` wrote `buckets` while requests read it, which can stop the controller with Go's `fatal error: concurrent map read and map write` once `RemoteStore` serves production traffic. All reads and writes now go through helpers that hold `r.mu` (`BucketExists`, `ListBuckets`, `CreateBucket`, `DeleteBucket`); `PutObject`, `GetObject`/`HeadObject`, `DeleteObject`, `ListObjectsV2` and `CreateMultipartUpload` use them. A test that runs these concurrently under `-race` is in `internal/s3api/remote_store_buckets_race_test.go`.
- The DataNode data-paths drop-in (`20-data-paths.conf`) wrote `RequiresMountsFor=` under `[Service]`, where systemd ignores it (`Unknown key 'RequiresMountsFor' in section [Service], ignoring`), so the service did not wait for the data disks to be mounted. `install.sh --path` and `examples/systemd/datanode-data-disks.conf.example` now put it under `[Unit]`. Nodes installed earlier keep the old drop-in until `install.sh --client --path ...` is run on them again.
- A paired DataNode no longer drops its node token when the Master rejects it. Before, a `403` on register deleted `datanode.token` and fell back to the already used one-time pair token, so the node could never come back. The token is kept, a rejected heartbeat (`403`) or unknown node (`404`) makes the node try to register again on every tick, a fresh pair token can still re-pair the node, and the replaced token is kept as `datanode.token.prev`. The token file is written through a temporary file and a rename. The Master only marks silent nodes offline; it never removes them or their disks, and they return on the next heartbeat (tests in `internal/datanode/keepalive_test.go`).
- `install.sh --update` treated a DataNode host as a Master. Source builds installed `mirymesh-controller` (binary and unit) on every host, and role detection returned "master" whenever a controller was present, so the update could create a database, write `controller.env` and start a controller on a DataNode. Source builds now install the controller only for the Master role. When both a controller and a DataNode are found, detection uses which service is enabled, then whether `/var/lib/mirymesh/datanode.token` exists, and chooses DataNode over Master in doubt. `--client` / `--master` still override detection.
- `install.sh` created the PostgreSQL role but not the database. `CREATE USER` and `CREATE DATABASE` ran in one `psql -c`, which PostgreSQL rejects (`CREATE DATABASE` cannot run in a transaction block), and `2>/dev/null` hid the error. Each statement now runs separately, errors are printed, and the installer checks that it can log in over `127.0.0.1` with the new password. A rerun resets the password of an existing role instead of failing.
- The Setup page asked for a DSN even though `install.sh` had just created the database. The installer now writes `MIRYMESH_DB_DRIVER`, `MIRYMESH_DB_DSN` and a generated `MIRYMESH_MASTER_KEY` to `/etc/mirymesh/controller.env` (root:root 0600) and loads it through a systemd drop-in, so the controller starts with the database configured. An existing master key or DB setting is kept.
- Source builds printed a `-Wdiscarded-qualifiers` warning from the bundled go-sqlite3 C code. `install.sh` now passes `-Wno-discarded-qualifiers` to cgo for that build only.
- A DataNode with several data paths ignored the `?disk=` the placement engine sends and always wrote to the first path. It now opens a store per configured path, writes to the requested disk (creating the bucket there), and rejects a `disk` that is not a configured path with `400`. Requests without `?disk=` (GET, HEAD, DELETE, list) search all disks, default disk first, so objects on the second and later disks can be read and deleted.
- Listing a bucket across several disks or DataNodes broke `continuation-token` paging. The DataNode now merges the listings of its disks (duplicates dropped, byte order, at most `max-keys` entries) and returns `is_truncated` and `next_continuation_token`; the controller merges the pages of all online nodes the same way instead of ignoring those fields. Nodes that answer with an error for a bucket are skipped.

## [1.0.0-rc.2] - 2026-10-24
### Fixed
- `install.sh` source builds (Master, including the prerelease channel) installed the old Alpine.js console. `frontend/dist` is git-ignored, so a fresh clone had nothing to embed and the controller fell back to `web/static`. The installer now builds the Vue console before `go build` and stops with an error if `frontend/dist/index.html` is missing.
- `install.sh` requires Node.js 22+ and npm on the host for Master source builds. It does not install Node.js. If either is missing or too old, it stops with an error before building, like the existing database check.
- `install.sh` removes `/usr/share/mirymesh/static` left behind by older installs, and its setup hints now point to `/setup`.

### Changed
- The release workflow, CI (`packaging`, `setup-smoke`) and the production `Dockerfile` build `frontend/` before compiling the controller.
- A controller built without the console now answers `503` with build instructions on non-API paths instead of serving a stale UI. `/api/*` keeps working.
- The DEB/RPM no longer ships `/usr/share/mirymesh/static`.

### Removed
- The Alpine.js console (`web/static`, `web/templates`) and its filesystem fallback in the controller (`resolveStaticDir`, `hasTokenGin`). The old `/static/*.html` URLs still redirect to the Vue routes.

## [1.0.0-rc.1] - 2026-10-24
### Added
- S3-compatible API endpoint (P0: Put/Get/Delete/List/Head, CopyObject, DeleteObjects, multipart).
- Placement engine (single/dual/triple/ALL, 95% quota).
- Per-bucket storage quota: `GET/PUT /api/admin/buckets/{bucket}/quota` and a Quota tab in the console. Writes beyond the limit (PutObject, CopyObject, multipart parts, console upload) return `507 InsufficientStorage`; `0` means unlimited.
- Replication engine (checksum, retry, interrupted-job recovery).
- Metadata evacuation / adoption (fan-out to datanodes, placement + auth presence snapshot).
- Management GUI (plain HTML/CSS/JS, no build) and `/api/admin/*` + `/internal/*`.
- Packaging via `nfpm` (DEB/RPM), `systemd` units, `Dockerfile` (distroless).
- CI: `ci.yml` (lint-test, e2e, packaging, linux-matrix, e2e-external).
- S3 SSE-C (AES-256-CTR, copy-source keys, multipart) and checksum validation (`Content-MD5`, CRC32/CRC32C/CRC64NVME/SHA1/SHA256, COMPOSITE / FULL_OBJECT multipart checksums, `x-amz-checksum-mode`).
- S3 `aws-chunked` request bodies: `STREAMING-AWS4-HMAC-SHA256-PAYLOAD[-TRAILER]` and `STREAMING-UNSIGNED-PAYLOAD-TRAILER` with chunk/trailer signature verification and trailing `x-amz-checksum-*` validation.
- `examples/`: NGINX (S3 / public read) and systemd drop-in samples.
- `install.sh --client` installs the prebuilt, sha256-verified static DataNode from GitHub Releases (falls back to a source build); the release workflow now publishes `mirymesh-datanode-linux-{amd64,arm64}` and `SHA256SUMS`.
- `install.sh`: accepts `--opt VALUE` as well as `--opt=VALUE`, accepts `--skip-db-check`, makes the DataNode data paths writable under `ProtectSystem=strict`, and passes the one-time pair token through a drop-in that is removed after pairing.
- Nodes page: the "Node を追加" command is now a `curl | sudo bash` one-liner that works on a host without a repository checkout.
- `install.sh`: interactive prompts (role, Master URL, pair token, data paths, confirmation) that also work under `curl | sudo bash`; `--yes` disables them. New `--update` flag updates an existing install in place (role auto-detected, config and data kept). Without a stable release it falls back to the newest pre-release such as `v1.0.0-rc.1`.
- Update notice: the Master checks GitHub Releases (`GET /api/admin/update`, `POST /api/admin/update/check`) and the console shows a dismissible banner when a newer version exists.
- One-click DataNode update: the Nodes page shows each node's version and an "更新" button (`POST /api/admin/nodes/update`). The DataNode downloads the release binary, verifies it against `SHA256SUMS`, stages it and exits with code 75. A root-owned `ExecStartPre` helper installed by `install.sh` replaces the binary (previous one kept as `.prev`) before systemd restarts the service. Run `install.sh --update` once on each existing node to enable it, or pass `--no-self-update` to opt out.
- DataNodes report their version when registering.
- `install.sh`: on a host that already has MiryMesh, the interactive run offers only "Update". New `--dev` and `--branch NAME` build from source; source builds (and the source fallback) now clone the `release` branch by default, and `--version TAG` still takes precedence. A fresh interactive install asks for Release or Dev.
- Branch flow `dev` > `prerelease` > `release`: the release workflow now runs on pushes to `prerelease` (publishes a GitHub pre-release, e.g. `v1.0.0-rc.1`) and `release` (publishes a normal release, e.g. `v1.0.0`). The branch decides the type instead of the words beta/dev/rc in the merge message, and a version whose suffix does not match the branch fails before anything is published.
- `install.sh`: new `--prerelease` / `--channel release|prerelease` and `MIRYMESH_CHANNEL`. The prerelease channel installs the newest release including pre-releases and builds source installs from the `prerelease` branch. `--update` stays on the channel the host is on (detected from the installed version or `/etc/mirymesh/channel`). A prerelease Master also sets `MIRYMESH_UPDATE_PRERELEASE=1` so the update notice offers rc builds. A fresh interactive install now asks Release, Prerelease or Dev.

## [0.0.0-dev] - Initial
- Repository scaffolding and Phase 0 baseline.
